# 治理节奏参考

> 何时读：设计治理排期 / 规则更新机制 / 专项治理时。来源：WebPurify living policies + ROOST coop，重构转写。

## 治理三节奏

| 节奏 | 周期 | 做什么 | 常见死法 |
|---|---|---|---|
| 日常巡查 | 每日 | 机审队列过流 + P0/P1 快速响应 | 只做这个，规则腐烂 |
| 专项治理 | 按需发起 | 单一乱象集中打击（水军专项/低质 AI 内容专项），有起止日与验收指标 | 运动式：有开始无验收，乱象卷土重来 |
| 规则更新 | 月度 | 复盘判例、校准分级阈值、更新规则文案 | 规则写完即冻结 |

**强制触发器**：规则超过 3 个月未 review → 触发更新流程（平台规则三月一变，静态规则必腐烂）。

## Living policies（活政策）

规则要以**病毒式威胁的传播速度**更新，机制两件：
- **快速更新通道**：新型灰产话术出现 → 规则增量发布，不等季度评审
- **Edge-case library（边界案例库）**：难判案例入库成为先例——判例库是活政策的地基

对冲设计：更新快则规则不稳定（用户无所适从）→ 设**规则版本号 + 变更公告**。

## 工作流闭环

```
检测 → 分级 → 处置 → 申诉 → 复盘 → 判例入库 → 规则更新 →（回到检测）
```

**复盘是最常被砍、却是唯一让系统变聪明的环节**。复盘会的纪律：开成"学到了什么"，不开成"谁的责任"——开了追责会，之后没人敢上报误伤。

## 人的可持续性

ROOST/coop 把 moderator wellness（审核员健康）做成平台级模块。中小平台转译三条：人审排班有上限；高有害内容轮换制；复盘不追责。治理系统先杀死审核员，是常见死法。
